# Native display construction

The checked display-output Source accepts a finite Frame Fore and exposes a
brightness-refusal Fore. Its retained encoder/selectors and TM1637 Host Call
execute in the shared ordinary kernel. Formatting, Look, page timing and sensor
acquisition remain upstream responsibilities.

## Preparation and scope

`PreparedDisplayKernel` supports fixed conformance stores and independently
admitted finite hosted stores. `PreparedAssignedDisplayKernel` instead consumes
canonical header/borrowed records against a trusted linked Make profile. Neither
entrance reconstructs portable software from advertised metadata. All selection
checks precede exclusive transfer of the actual initialized software owners.
Dropped preflight preserves readiness; successful transfer withdraws those owners
and replay refuses. Play allocates nothing.

`PreparedDisplayOutput::display_layout` derives record pins, computation
configuration bytes and exact local Fore pins from a normally sealed Plan.
The display-offer producer emits the compiled firmware module and bounded
uninstalled transfer. The module contains no live Host, Boot or Plan identity;
the same selections produce identical acceptance material across Boots.

Schema 7 local Fore pins are explicitly opted in and do not describe network
Lines, peers, membership or caller authority. Legacy entrances refuse them.
Runtime value validation and permission to submit a Frame remain separate from
matching the ABI digest. `ValidatedAssignedDisplay` retains checked numeric
tables and Fore pins without borrowing ingress bytes or consuming software.

Root admits finite record views, value/Sign backing, boxed kernel storage and
preparation/control headroom before allocation. The kernel requirements and
owner reply share the same active-profile bound. Native binding and execution
context backing have separate admission checks. Root memory guards are unchanged;
a CPU allocation estimate is not physical heap/stack admission evidence.

## Authenticated Root lifecycle

The `display-ready-root` profile uses the existing owner control protocol:

1. Stage the bounded transfer against independently linked Source, layout and
   configuration records. Retain its owned bytes, validated tables and seal.
2. Authenticate Reserve against the current offer epoch. Correlate the full
   Plan/fragment identities and expected next Root Play with the admitted token.
   Bind the assignment seal and Body/Wake provenance without issuing possession.
3. Authenticate Prepare. Issue finite display possession and bind the retained
   GPIO owner against the independently validated assignment, then construct the
   dormant kernel from actual retained software. This releases binding scratch
   before allocating persistent kernel stores. Each transfer withdraws its ready
   advertisement. Assemble the exact kernel and
   driver into one context, then register it with the existing Embassy executor.
   Wait for actual task custody to report `ready-held` before acknowledging.
4. Authenticate Start using the shared held-start/release gate. It acknowledges
   idle held custody and advances no Step or electrical operation.
5. Authenticate Release to let the registered task pump the ordinary kernel.
   Single-use pending Host Calls cross `DisplayService`; completion preserves
   request correlation and distinct denied/cancelled/failed outcomes.
6. Cancel revokes native permission and cancels the kernel. Retire requires
   terminal task acknowledgement, successful cleanup and revoked idle custody.
   Root accepts only the exact returned Play scope/provider generation. Dropping
   a handle never implies provider reuse, a fresh generation or new authority.

Partial preparation retains already transferred custody for an authenticated
retry or cleanup; it does not claim rollback. A bound output can be revoked and
retired even when later kernel preparation refused, without inventing a kernel
or advancing a Step. Task status reports context/static
future bytes, exact held/terminal progress, cleanup and native custody separately.
The task slot is one-use in this Boot. Reoffer remains unconnected.

This remains a two-frame construction profile. There is no admitted live Mask
client yet: a released task reaches `waiting-input` and sleeps until cancellation
rather than spinning or inventing Frames, timers or observations. Input wakeup,
refusal delivery and continuous sampling/Mask composition still require their
planned typed connection. Root receipts do not claim full Body installation.

## Attended dormant preparation

`cargo xtask prove environment display-output esp32-readiness --flash --prepare`
provisions the existing private host owner key, compiles its public trust into
the diagnostic, observes/stages the current output assignment, and admits the
actual MCU to a Body born from that checked display Source. A retained Rust Body
owner proposes the exact output Plan and signs Inspect, Reserve and Prepare.
The shared carrier only transports those bounded frames.

Success requires the registered display task to report actual `ready-held`
custody, positive context/future backing, issued idle native permission and zero
steps/software/native calls. No Start, Release or Frame is sent. Refusal retains
its exact response and Root memory observations; it cannot claim a Body start or
physical output. This command leaves a construction diagnostic, so operational
firmware restoration is a separate attended recovery step. The preparation proof
does not install the continuous climate appliance.

The before/after physical preparation receipts are in
`../evidence/2026-10-24-display-native-preparation/`. Kernel-first construction
refused binding capacity. Binding-first construction preserved all guards and
reached actual ready-held task custody, with Root's highest observed peak at
105,460 of 114,688 bytes. This establishes dormant preparation headroom for the
two-frame profile, not active output or complete appliance memory closure.

The optional `esp32-readiness --flash --run-idle` extends that same preparation
through attributed Start/Release, read-only input-wait observation, Cancel and
Retire. The retained host Body owner changes lifecycle only after verifying
Boot-signed transition receipts against the admission-pinned key. Cancellation
is attempted even if release/observation fails; unknown quiescence preserves
unresolved evidence rather than recording a Lull. No Frame producer is admitted
by this mode, so successful kernel startup/input wait cannot prove physical
output or continuous Mask execution. Operational image recovery remains separate.

## Mask Frame composition

`PreparedDisplayFrame` reserves only the canonical `Tm1637Frame` composers from
its independently checked linked type. It contains no packet-expression program
or evaluator. Repeated composition and exact Frame validation allocate nothing;
invalid brightness remains typed input for the authored encoder's refusal path.
The existing packet helper delegates Frame composition to the same owner.

The retained host owner's interpretation now produces canonical Frame bytes
rather than independently executing packet policy. Its attended capture saves
those bytes and their digest with the originating Face revision/Show. The CPU
integration proof feeds temperature and RH Frames from an actual retained Body
Face through the checked output graph, original kernel, selectors and actual
TM1637 Host Call service with explicit CPU pins/authority. Both outputs drain
without Play allocations; the Face stays unchanged. This is interpreted Mask
input followed by CPU output execution, not an installed Mask-role route, caller
admission, wakeup wiring or physical delivery. The MCU still has no admitted
live Frame producer.
