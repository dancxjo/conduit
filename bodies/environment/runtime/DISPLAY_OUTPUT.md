# Ordinary display output construction

`PreparedDisplayKernel` executes the checked display-output Source in the shared
fixed scheduler. `prepare` retains the fixed-store conformance profile.
`prepare_with_storage` accepts independently prepared finite value and sign
stores, and puts the unchanged scheduler in boxed custody through its existing
boxed constructor. This avoids returning the large scheduler by value through
preparation frames. Heap-backed stores still have fixed admitted capacities;
Play does not allocate.

Both entrances validate the exact Plan and lowering, numeric kernel tables,
current retained software selection, and output shape before transferring the
software. Supplied stores must be empty, provide at least twelve value slots
and 12 KiB of live value capacity, cover the lowered sign budget, and reserve
256 remote-sign slots for the finite Fore profile. Root separately admits the
stores' backing, the scheduler allocation and temporary construction headroom.
This API is not an allocator admission guarantee or effect authority.

The public `cargo xtask prove environment display-output` proof runs the actual
Source with both fixed and finite hosted stores. It checks two successive
frames, invalid brightness, pre-service cancellation and zero allocation during
Play. Undersized values, insufficient sign or remote-sign backing, occupied
values and occupied signs refuse without consuming retained software owners.

This construction prerequisite is tracked by #6374. It does not install the
output graph on the MCU, authenticate a Fore caller, issue a native capability,
start a Body, or replace the live bench's coordination loop. Compact assignment
of this graph's external Fore, combined sensor/Mask/output admission and physical
execution remain required for the continuing native appliance.

## Compact native preparation

`PreparedAssignedDisplayKernel::prepare` accepts the canonical header and
borrowed records, a trusted linked Make profile, the current Root scope, retained
software and independently admitted finite stores. It does not deserialize a
rich Plan or reconstruct software from advertised descriptors. The shared
assigned-table builder and original kernel constructor preflight the complete
numeric topology before exclusive software transfer.

The retained-owner check matches current Host/Boot/offer epoch, Source family,
exact kind/implementation/artifact identities, actual program/selector text and
pure Host Call ABI. All three initialized portable owners are checked before
any is transferred. A dropped preflight keeps them available; a successful
transfer withdraws them from future offers and replay refuses as already
selected. There is no automatic epoch increment: Root owns that transition.

The compact result retains numeric Fore pins. Root must independently retain
and enforce their typed value contracts, bind the actual GPIO owner and native
authority, admit complete memory/work and issue Body start before stepping.
Preparation creates no native provider, capability possession, Line or Body.
The checked display CPU proof now uses this production preparation entrance,
including stale epoch, foreign Source/Boot, occupied storage and zero-frame
refusals followed by successful execution of the original owners.

## Trusted firmware layout provisioning

`PreparedDisplayOutput::display_layout` derives resident record pins, computation
configuration bytes and exact local Fore pins from the normally sealed output
Plan. The display-offer preparation example emits `display-layout.rs` alongside
its assignment. This build input contains no live Host, Boot or Plan identity;
the same source and selections produce identical layout material across Boots.
Incoming assignments still require current scope, retained owners and authority.

The ESP32 `display-ready-root` profile includes that generated module against the
production compact runtime types. This is preparation only: the module grants
no Fore access, issues no native possession and starts no output Play. The
existing live bench remains the deployed image until authenticated assignment,
complete admission and continuing Body execution are connected.

`ValidatedAssignedDisplay::admit` separates topology staging from software
transfer and kernel construction. The private token owns checked finite tables
and Fore pins without borrowing ingress bytes. Admission checks the linked
layout, current Host/Boot, local Fore, native call shape and ordinary scheduler
geometry without allocating. It issues no authority and does not verify current
software availability; retained-owner selection still occurs during preparation.

The ESP32 Root display reservation entry point accepts this validated token,
correlates full Plan/fragment identities with its compact identity and checks
the expected next Root Play before consuming the global sequence. The signed
owner wrapper additionally binds the assignment seal and Body/Wake provenance.
CPU tests exercise production reservation/authentication code with explicit
Boot/entropy substitutes. The display profile connects staging to signed reservation. Native capability
issuance and kernel preparation remain later phases than ingress; reservation
reserves no physical output operation.

Root can now issue bounded display possession for the reserved validated output
assignment. It checks the exact local Fore pins, current retained provider,
selected native node and finite Root-selected frame budget before committing
issuance state. Failed checks preserve issuance; successful issuance is fenced
against replay and transfers no GPIO owner. The existing driver binder then
transfers the retained owner exactly once without electrical effects.

CPU evidence uses production Root issuance with explicit entropy/Boot/pin
substitutes. Complete installation and start, physical execution
and display retirement/reoffer remain unconnected to running Body control. No automatic provider reuse
or fresh generation is inferred from dropping a handle.

`RetiredDisplay` now captures private Play scope and provider generation from
an actual revoked idle driver before consuming it. Root ends display issuance
only for that exact returned custody; a foreign Play or repeated completion
refuses. Sequence and generation never rewind, so even a newly reserved Play
cannot issue the returned provider at its old generation. Sampling retirement
preserves shared Play custody while display possession remains outstanding.
The CPU test performs issuance, retained binding, revocation and retirement
without pin operations. MCU Body control and reoffer remain unconnected.

## Bounded display ingress

The display preparation profile now routes the existing assignment transfer
command through its independently linked Source/layout/configurations. Staging
admits finite record backing, an owned transfer and a control reserve before
allocation; it retains the checked tables and transfer seal without selecting
software or GPIO owners. The normal signed owner reservation uses this staged
display token and its exact seal. The sampler profile retains its original path.

The host display-offer producer emits the uninstalled bounded transfer. The
observed-plan fixture produces 2,427 bytes against the 8 KiB transfer limit.
CPU tests exercise the production staging helper, owned-byte isolation and
capacity/Boot/Source refusals. Both ESP32 profiles compile. No new image has been
flashed: live UART staging, kernel installation, Body start and physical output
still need verification before replacing the working bench.

The signed Prepare path in the display profile now constructs and retains the
ordinary output kernel from that transfer and the actual retained software.
It admits canonical value/Sign backing, record views, boxed kernel storage and
8 KiB preparation/control headroom before allocation. The Sign log exposes its
canonical backing estimate without exposing private lifecycle representations;
a test compares the estimate with prepared retained storage.

This entrance remains a two-frame construction diagnostic. It withdraws the
old offer epoch on successful preparation and leaves the kernel unstepped.
Portable construction alone issues no native possession or Body start. CPU tests cover memory
refusal before transfer, successful construction and replay refusal. ESP32
compilation passes; physical memory admission and continuous Mask scheduling
are still unverified. No display image has replaced the working appliance.

Owner replies now report the active profile's preparation bound rather than
always reporting the sampler's bound. Display construction and reporting share
one requirements function. The CPU allocation probe checks that one byte below
the bound refuses with no allocation or reallocation, while exact-bound
construction succeeds and its total requested allocation bytes stay within the
admitted amount. This is CPU backing evidence, not MCU heap or stack proof.

Signed Prepare now follows dormant kernel construction with exact Root-issued
TM1637 binding. Binding admits record views, owned driver storage and separate
contract/control headroom before allocating; it checks the retained assignment
and reservation and transfers the actual ready pin owner exactly once. Bound
pins no longer appear in readiness advertisements, and owner replies report
possession independently of Body installation or start. If binding refuses after
kernel preparation, that dormant kernel remains held for an authenticated retry.

The production binding helper passes CPU proof with pin methods that panic on
any electrical operation, capacity refusal preserving readiness, and repeated
transfer refusal. Both ESP32 profiles compile. Physical binding and memory
admission remain unverified, and worker execution is not connected.

The display profile accepts authenticated, reservation-matched Start as
`StartedHeld` using the same held-start/release transition functions as the
sampler task. It checks actual issued idle driver custody and an unstepped
kernel. Start runs no Step or pin operation. Cancel revokes that held driver
and cancels the kernel; Retire consumes revoked idle boxed custody and completes
Root retirement. Release explicitly refuses until an executor owns the context.

CPU tests cover shared transition refusal/replay/cancellation and production
boxed retirement preserving ownership before revocation. Both target profiles
compile. These checks do not prove full Body installation, physical lifecycle
commands, continuing execution, sensor-to-Mask integration or recording.

`DisplayService` now services one ordinary-kernel-selected Host Call using the
retained selectors or native driver. Taking a request creates a non-cloneable,
single-use pending token; completion preserves its node/request correlation and
machine-readable denied/cancelled/failed outcomes. Failed completion discards
any uncommitted output value. This adapter advances no scheduler Step and owns
no page policy, timing or Fore admission.

The existing fixed, hosted and compact output CPU proofs now use this production
service while retaining exact packet assertions, successive frames, semantic
brightness refusal and cancellation checks. All eleven display tests pass,
including zero allocation during Play and no pin effects after cancellation.
The ESP32 profile compiles. Background execution and Release remain unconnected.

Prepare now assembles the retained output kernel and bound native driver into
one boxed execution context after separately admitting its storage and control
headroom. Scope mismatch or a missing side refuses before transferring either.
Context allocation refusal leaves earlier custody held for authenticated retry;
Start requires the actual idle context. Replies report its actual context size.

The context pumps the unchanged kernel through `DisplayService`, with cancellation
between bounded polls, progress counters, terminal cleanup and consuming provider
retirement. It owns no Frame producer, formatting policy or clock. CPU proof
covers zero-operation assembly, immediate cancellation with zero Steps, replay
fencing and exact returned custody. All seventeen Root-control tests pass;
ESP32 compilation passes. Task registration, Release, typed Fore client wakeup,
normal physical execution and continuous sensor/Mask composition remain required.
