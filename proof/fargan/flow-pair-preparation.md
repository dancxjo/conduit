# Immutable Flow-pair preparation scope

`PreparedFixedFlowPairProfile::prepare_immutable_no_cache` is a separately named,
closed capability for the six original Source-derived numeric Flow-pair kinds.
It retains the complete original pair Type, exact capability offer and both
original finite-F32 validation envelopes. It preserves the existing pair
constructor and Step validation; no values, predicates or transport limits are
weakened. Other kind identities refuse. A build enabling `hosted-catalog-cache`
refuses this entrance: that cache's retained allocations are not its owned charge.

Before any catalog/checker allocation, this entrance requires the reviewed
immutable-profile reservation: 64 MiB cumulative requested allocation payload,
1 MiB simultaneously live preparation payload, and 32 KiB retained payload.
These are explicitly scoped reservations for the pinned implementation, compiler,
SDK, no-cache configuration and six exact inputs. They are not a generic checker
allocation algorithm or a portable allocator/whole-memory claim. The standalone
all-six probe and exact artifact/source/toolchain hashes are retained with the
checkpoint receipt. The observed maxima are 63,575,483 requested bytes,
1,009,989 peak bytes and 31,683 retained bytes. Each ceiling one-under refuses
before allocating. Any implementation/profile/toolchain change requires reviewing
this finite reservation and rerunning the exhaustive gate.

Per-Back `storage_reservation` instead derives its bound from the actual Core
bounded pair encoder and the original finite envelope clone capacities. It does
not run a catalog/checker or normalize the Type. Both requested and retained
limits are checked before constructing or cloning. Every one of the six profiles
has allocator/refusal coverage. Actual retained owned capacities equal the
accounting getter; source spare capacities conservatively bound fresh clones.

The factory's new bounded entry accepts an already prepared immutable profile.
It checks complete capability-offer equality against its selected placement and
runs the unchanged placement verification before allocation. It includes the
concrete trait-object Box payload in its per-Back charge. A foreign profile
refuses without allocation. Existing legacy preparation remains unchanged.
Factory/Plan/catalog construction, shared profile ownership, Arc headers,
allocator bookkeeping, inline return owners and stack are separate. The legacy
factory's BTreeMap construction and full Plan verification have not become an
admitted whole-driver preparation merely because per-Back preparation is bounded.

This component does not establish actual trained execution, complete working
memory, pressure-resume equivalence, target runtime or #5218 acceptance. The
original proper-IPA occurrence/context/variety/revision and overlapping gesture
requirements, same-intent projectors, declared losses and attended contrasts stay
independent acceptance gates.
