# Input-consuming mathematical enclosure preparation

This private #5392 development slice proposes `math/enclose` as an ordinary
input-consuming mathematical projection boundary. It receives the existing
`MathematicalValue` encoding, with a typed `MathematicalEnclosureRequest` startup
record containing `maximum-width`. Its result retains the exact source bytes,
rational lower and upper endpoints, actual width and requested maximum width.
The result is a distinct interval record, rather than an exact scalar alias.
There is no new numeric literal language, Unit coercion or IEEE reinterpretation.
The name and profile remain local preparation until ordinary review/admission.

The checked Kind retains finite input/output/startup extents and the existing
exact request/property law. The Planner's existing exact-realization filter
requires the offered request to equal the authored request. The Std Host offers
the reviewed 32-node/depth-16 interval engine with bounded constant terms and
root refinement. It divides the requested width by 64 for each leaf's refinement
target; the final composed interval must independently satisfy the full requested
width. That heuristic is a refinement strategy, not a proof that every supported
expression can meet the request. Unsupported computations or insufficient
refinement/work/tolerance refuse.

Installation reconstructs the request, prepared storage and typed bounds and
compares the selected Kind, profile, artifact, properties, Fores and operational
limits. The artifact binds the consumer, encoder and shared interval evaluator
sources. The admitted numerical-work figure includes the evaluator ceiling and
a conservative allowance for the structured composer/validator's separately
metered checks. This accounts for component numerical work, not total kernel
fuel, whole-process memory, latency or WCET. Payload figures exclude allocator
overhead and stack storage.

The Back validates and evaluates actual incoming data during Play. It reuses
`PreparedMathematicalEnclosureEvaluator`, prepared structured composers and the
existing generic projection domain/policy/report. Report identity binds source,
endpoints, width and the actual numerical policy parameters. Kernel Signs retain
Plan/Play execution custody separately. The result record alone is not a
self-authenticating producer certificate: a later independent consumer must
verify its typed envelope and claims against retained source and requirements.
`PreparedMathematicalEnclosureVerifier` prepares that exact schema and producer
requirements, then borrows the incoming record and independently recomputes the
source/bounds/width claims. It rejects changed schema, declared policy, source or
claims and applies the receiving consumer's width separately. Its reserved
validation allowance is charged before parsing; arithmetic and refused attempts
also consume the caller's smaller prepared work ceiling. Storage admission counts
the schema, container and evaluator scratch. It returns only recomputed fields.
It attests numerical validity, not producer execution or physical/source authority,
and does not introduce another projection/fidelity protocol.

Before consuming input, the Back checks output pressure and fuel. Only a complete
successful evaluation/encoding may stage output; the ordinary commit publishes
it. Cancellation discards staged output. Closed input completes without an
invented value. Failure never authorizes publishing a previous success.

The initial installed proof sends dynamically supplied π/180 and principal
sqrt(2) through an authored exact transport Plot, checked/expanded Source, sealed
Plan, selected Std Back and ordinary kernel. It checks identical source bytes,
independent established decimal brackets, width arithmetic and admitted width.
Both successful Plays observe zero allocations after Play start and unchanged
Value storage capacity. A zero-width π attempt emits no output; a subsequent
exact rational input succeeds using the same Host and Plan. These are dynamic
input-consuming tests, distinct from the older startup-frozen numerical receipts.
Raw logs retain their exact test/source identities; final validation is recorded
separately rather than inferred from this description.

The input-profile checkpoint passes all 852 Std library tests with 17 existing
ignored tests, all 193 catalog tests, and strict Std/catalog all-target Clippy.
The actual CLI corpus also executes an existing `math/radians(1°)` construction
through the new consumer, checks source and requested-width equality in an
ordinary inspected result, and reaches Completed with a verified Source/Plan
identity. Its zero-width variant reaches the numerical Back and refuses with
`InvalidInput`, detail 4, without success output. Ordered general
`MathematicalValue` comparison is not assumed; actual endpoint/width inequalities
are checked independently in the kernel corpus. Source-specific logs/bundles
distinguish these checkpoints from subsequent verifier work and stable acceptance.
Three independent Core record-verifier tests cover schema/extent/storage/work
admission, source and claim forgery, changed policy, stronger/weak consumer limits,
zero-width exact results, allocation-free refusals and recovery. The original
input-profile checkpoint remains separate from this later verification API.

## Component cost capture

The [raw cost records](evidence/input-mathematical-enclosure-cost-20261019.json)
retain 16 trials per specimen in both unoptimized and optimized Cargo test
profiles on Linux x86_64, Intel Core i7-12700, Rust 1.98.1. Each trial prepares a
fresh Back in a warmed process, performs one untimed warmup, then measures four
calls with thread CPU and monotonic wall clocks. Allocation-probe and timing
overhead are retained. The optimized profile uses optimization level 3, 16
codegen units, LTO off, debug assertions off and overflow checks on.

| Exact input | Optimized median CPU per repeated call |
| --- | ---: |
| 1/3 | 0.01545 ms |
| π/180 | 28.974 ms |
| principal sqrt(2) | 6.469 ms |

All 192 timed calls per profile observe zero allocation/reallocation calls and
unchanged prepared capacity. The source and complete result digests match across
both compiler profiles for all three specimens. Fresh preparation remains
allocation-heavy: median thread CPU across 48 fresh preparations is 7.628 ms,
and every observed trial records 27,844 allocation calls. The
captured Back-owned state/buffer payload is 172,568 bytes; the installed property
also counts the outer driver container. Allocator overhead, stack, caller data
and kernel arenas are excluded.

This measures `Back::new` and its numeric/encoder/report evaluation, excluding
Host advertisement, Source checking, Plan construction, kernel queue/Sign costs
and output delivery. It is not whole-Play throughput, a product-release profile,
cross-target performance, native-equivalence evidence or WCET. The earlier
unoptimized records are retained alongside the optimized capture.
The installed value-port Back emits once per Play. Repeated private evaluation
calls are a component measurement; this capture does not amortize preparation
over several admitted values in one Play.

There is no installed browser/no_std/device profile, machine-float computation,
symbolic Quantity wire, separate Unit-coordinate projection, approximate-input
composition, physical fusion, DSP/ML acceptance, or throughput claim here. The
full #5392 acceptance corpus and exact-source integration/publication gates remain
open. No second numerical implementation PR is opened while #6005 is in flight.
