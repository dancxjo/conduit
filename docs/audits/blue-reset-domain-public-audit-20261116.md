# Blue ESP32 reset-domain audit — 2026-11-16

Scope: read-only source/document review; no device, serial port, flasher execution, reset, flash contents, or keys accessed. No runtime authority/claim state changed. Existing issues #6340/#6409 remain the relevant gates.

## Qualified command and implementation

The reviewed controller invokes each espflash command without `--before`, explicitly uses `--after no-reset` for read/write/readback, then `board-info --after hard-reset`. These are independent invocations: **no-reset applies after an operation; it does not suppress the next invocation’s default before-reset**. The controller checks subprocess success and physical MAC but does not measure EN. Requested tool qualification: espflash 4.5.0, SHA256 `03869e52b4ab6433720087eb8b895a94852e0c6f1e44b07c184b1dfeaab2f6ae`; supplied qualification was not independently reproduced: the controller’s tool path is absent in this local environment. Version-tag source alone does not authenticate the executable bytes.

[espflash v4.5.0 CLI ConnectArgs](https://github.com/esp-rs/espflash/blob/v4.5.0/espflash/src/cli/mod.rs#L64-L76) selects `default-reset` before and `hard-reset` after unless overridden. [Connection dispatch](https://github.com/esp-rs/espflash/blob/v4.5.0/espflash/src/connection/mod.rs#L286-L299) runs the reset strategy unless before=no-reset/no-reset-no-sync; [after dispatch](https://github.com/esp-rs/espflash/blob/v4.5.0/espflash/src/connection/mod.rs#L405-L410) maps hard-reset to hard_reset.

[Exact reset implementation](https://github.com/esp-rs/espflash/blob/v4.5.0/espflash/src/connection/reset.rs): hard_reset calls reset_after_flash. For the ordinary USB-UART path (CP2102 rather than integrated USB-JTAG), it waits 100 ms, asserts RTS, waits 100 ms, releases RTS. The implementation uses RTS; the ResetAfterOperation enum’s DTR prose is inconsistent with the executable function. On Unix/local serial, default before-reset tries UnixTightReset (normal/extra delay) then ClassicReset (normal/extra delay); both request EN low for 100 ms, then release EN with GPIO0 low for download mode, finally release GPIO0. Which retry actually succeeded requires operational trace evidence.

## Actual electrical boundary and remaining assumptions

[Espressif boot-mode documentation](https://docs.espressif.com/projects/esptool/en/latest/esp32/advanced-topics/boot-mode-selection.html#automatic-bootloader) describes active-low RTS/DTR, RTS connected through reset circuitry to EN/CHIP_PU, and DTR to GPIO0; it explicitly identifies board-circuit dependencies and unreliable third-party reset implementations. GPIO0 low at reset selects ROM download mode. [ESP32-WROOM-32 datasheet §§3.6,5.3](https://documentation.espressif.com/esp32-wroom-32_datasheet_en.html) specifies CHIP_PU low below the reset threshold for at least 50 microseconds; the nominal 100 ms host delay exceeds this only **if the physical circuit produces the corresponding pulse**.

[ESP32 TRM v5.9 §7.1, printed pp.165–166](https://documentation.espressif.com/esp32_technical_reference_manual_en.pdf#page=165) distinguishes: CPU reset changes CPU registers only; Core reset resets digital registers including both CPU cores and GPIO; System reset includes RTC registers. RAM is not cleared by these reset levels. Thus a one-core software reset or fresh nonce alone cannot establish peripheral/DMA retirement. A correctly delivered CHIP_PU chip-reset boundary ends the former CPU execution and resets on-chip execution machinery; no old Source task can continue through chip shutdown/reset merely because RAM bits survive. The audited tool is attempting that hardware boundary, not a Source-level receipt. Neither host API success, JSON, nor MAC independently measures voltage/duration/reset cause on this exact board.

Root’s reported authenticated fresh Boot after the reviewed image is positive evidence of new application execution. It does not by itself measure every reset domain, establish circuit topology, or clear the retained Root claim. Combining it with the reviewed physical-reset route is a conditional hardware argument, not direct waveform evidence. No additional reset is prescribed by this audit.
