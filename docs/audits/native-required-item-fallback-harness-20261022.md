# Required-item owner fallback scenario

For #6190 and #5628, the existing supported
`cargo +stable xtask make conduitos live-owner-todo-action-proof` command accepts
`--required-item-fallback`. Its existing exact installed-source, isolated fork,
protected checkpoint, coordinated activation and owner Face-read guards remain.
The scenario additionally requires `--fallback-action-id`,
`--fallback-tab-count` and `--fallback-status`; the ordinary first action must be
`--expected-action-id todo.complete.task-1`. Both Tab counts are explicit bounded
native keyboard navigation, not DOM or simulated owner calls. The fixture must
start with the actual offered compact/phosphor 100% flat selection and task-1.

The four-refresh sequence is:

1. Shift+F8 selects the reviewed required-item component while preserving Face
   and expression. A complete acknowledged realisation is decoded and captured.
2. Complete task-1 through the actual native route. Require its removal, explicit
   recipe fallback, fresh acknowledged Show, unchanged selected configuration
   and expression, and independently read complete owner Face equality.
3. Enact the explicitly named remaining action while the generic fallback is
   still selected. Require its exact predecessor Show/Face/revision and an
   acknowledged replacement, then reread the authoritative owner Face/status.
4. F6 selects the ordinary flat component, comparing that identical final Face
   and expression with the preceding generic fallback presentation. No Body
   action may be emitted by either selection. Require exactly two owner actions.

Each receipt identifies the source, ISO/build/candidate, complete observations,
PNG records, isolation inventories, and the four-refresh bound. The comparison is
explicitly generic fallback versus ordinary flat component; it does not claim a
second independently selected provider-free graphical agency.

A former selected-Show interaction is constructed before mutation and checked
against the actually observed post-completion Face/Show using canonical
`FaceInteraction::validate_against`. Its receipt explicitly says deterministic
admission, **not installed replay enactment**. The guest has no supported stale
input injection entrance. The harness never resubmits the successful action or
replays an uncertain outcome. Additional live stale-route evidence, if required
for closure, remains separate work rather than a fabricated harness claim.

Focused deterministic specifications cover truncated/unbounded records and exact
accepted-action predecessor/Face/revision/refresh matching. Formatting and
whitespace checks were performed. No compilation, tests, QEMU, image rebuild,
release, CI or acceptance run was performed for this change. The scenario is
preparation for the next serial native acceptance step, not issue closure.

Root review tightened the scenario to require the actual required-item recipe
identity and to recompute its slot/action refusal against the complete observed
post-completion Face. Unrelated geometry fallback cannot satisfy this witness.
The existing action command now refuses when the owner return route is absent,
rather than succeeding with its read-only Face receipt. The remaining action is
performed through fallback before the same-Face ordinary component comparison.
