# Face, checked component recipes and visual expression

Issue #5364 owns this separation. The initial implementation is under development;
source checking, actual native/browser rendering and acknowledged occurrence proof
must all be established before claiming the complete vertical.

## Ownership

Face (`Presentation` in the existing Rust API) owns subjects, exact relationships,
semantic order, names, availability, disclosure and typed source actions. Todo's
accepted model/scan remains the sole owner of its item state and transitions.

An ordinary checked component Plot owns fixed semantic slots, structural groups,
original action references, meaningful/focus traversal and admitted reflow limits.
The component recipe is source-authored canonical startup configuration. Its
selected renderer consumes that configuration from the actual planned placement;
a copied Fore hash or handwritten parallel semantic tree is insufficient.

`VisualExpression` is the initial finite visual Look facet, not a new multimodal
Look language. Density, palette, text scale and restrained motion are independent
expression preferences. The closed schema cannot carry semantic selectors,
actions, argument contracts, labels, role overrides, keyboard bindings, focus
order or component topology. #5368 owns the common optional multimodal facets;
#5377 owns declaration syntax. Neither is presumed implemented here.

The selected Mask/Host owns resource realization, platform accessibility,
measurement, geometry and actual Show acknowledgement. User accessibility and
hard Host limits outrank authored expression. Structured value bounds alone do
not establish readable geometry or reachable controls.

## Checked source and realization boundary

The ordinary Mask Fore stays `face: Presentation` in, `show: Show` and closing
`interaction: FaceInteraction` out. The component embeds its recipe and exposes
only a typed expression startup parameter. Changing expression may change the
expanded Plot, selected Mask Plan, Mask Play and Show. The component's original
checked source/Fore and recipe remain identical, as does the unchanged owner
Face and Todo Play/state.

The shared preparation gate must inspect the actual checked document, expansion
provenance and canonical configuration; verify the immutable selected Plan and
placement; admit the recipe and expression; and derive traversal from original
Face references. The gate independently reproduces checked expansion and the ordinary Plan using retained actual Host offers, placement choices and bounded Fore limits. It follows compiler-owned ancestor segments, including names containing slashes, and the admitted checked Back definitions. The literal recipe belongs to the exact expression-only checked component; later steps must explicitly forward its recipe and expression parameters. Stable component source/Fore evidence is separate from its changing invocation occurrence. Plan reconstruction is not a resource reservation or Show acknowledgement.

Native/browser realizations must consume that same admitted
traversal rather than independently reconstructing application meaning.

Choosing different Backs of the same rendering Kind preserves the checked
component contract. Choosing different compile-time Plot/Kind parameters can
change checked specialization identity and must be recorded honestly.

## Replacement and failure

A Look-only replacement retires the prior Mask Show and reseals its route,
without Lull/Wake, workload replacement or Todo reducer restart. It renders the
same exact Face revision and acknowledges the actual new DOM/scanout occurrence.
Old Show return interactions refuse before source command admission.

Invalid visual encoding/version/identity/text scale selects the finite Phosphor
fallback request, with the refusal recorded in `VisualExpressionOutcome`.
Accessibility constraints are then applied to the fallback too and retained in an independent override record, so fallback does not hide user requirements. Unsupported
requested text scale falls back if a usable user-respecting scale exists.
Impossible user text capacity is a distinct Host refusal: the Mask must select
an admitted reachable generic/linear fallback, not hide required meaning or
claim successful styling. Actual DOM/native execution must prove that join.

Look/recipe/Host identity and accepted/fallback outcome belong to realization
evidence bound to the actual acknowledged Show. They do not enter Face identity.
Focus, scroll and decorative motion may remain Mask-local; they cannot dispatch
new domain actions. Optional detail must remain genuinely reachable.

## Compatibility

Preserve `ApplicationTheme`, `APPLICATION_THEME_VERSION = 2` and
`conduit.presentation/phosphor@1`. Existing finite bytes remain a compatibility
carrier. Their responsive breakpoint/grid-min fields do not give a new Look
unbounded layout authority: the configured structural recipe/Mask must own and
admit layout selection and reflow. The new visual admission does not reinterpret
old bytes as certified expression or remove existing contrast/focus safeguards.

## Required proof

Palette enum admission is not contrast certification or keyboard proof. The structured startup carrier and custody fixtures do not establish structural recipe interpretation or production renderer consumption.

The first application reference is unchanged accepted Todo source, one actual
Body/owner Play and Face, and the same source-checked component under Compact
and Spacious. Compare semantic identities, action arguments/availability,
relationships/order/disclosure, traversal and source basis. Then exercise a real
typed command through the current acknowledged Show. Admit maximum item/text
bounds without hidden storage growth, missing required content or unreachable
input. Prove unknown valid meaning through truthful generic fallback.

This first reference does not waive the second independent structural recipe,
dramatically different Looks, contrast/forced-colors/reduced-motion/large-text/
keyboard proof, compatibility migration or supported native/browser execution.
Deterministic admission tests, actual renderer execution, emulator/native and
physical/human evidence remain different proof classes.
