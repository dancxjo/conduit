# The canonical Conduit lifecycle journey

Status: in progress, 2 November 2026. This chronological account is an executable
delivery record, not a claim that the destination below is already implemented.

## Destination and invariants

An existing authoring Host runs Crèche, births a Body, and provides ordinary
authoring and checking of Host definitions in Conduitese. Crèche accepts a saved
`.host.conduit` definition or supports creating one, resolves its construction,
and uses shared Make to produce the destination artifacts. The provisional
user-facing word **Seed** refers to the existing Spore construction family; this
record does not change a wire schema or claim that provisional vocabulary is a
new architecture.

Crèche stays on the authoring Host. It may offer an admitted flashing, transfer
or installation carrier, or retain artifacts for an explicitly recorded human
transfer. The destination executes its prepared realization and joins the same
once-born Body through actual invitation/membership. Making an artifact, writing
it, observing a Boot and admitting a member remain separate outcomes.

The Body's ordinary Plots then compose sensing, retained history, computation
and human interaction. One coherent semantic Face supplies multiple Masks;
checked Looks may be reused across those Masks without changing the underlying
quantities, actions, provenance or failures. Device-specific provider/wiring
truth remains in Host construction and actual initialized offers.

## Milestone acceptance

| Stage | Required witness | Current result |
|---|---|---|
| Existing Host and Crèche | Actual installed Host/Boot and acknowledged encounter | Verified installed Linux service, Birth encounter and subsequent Crèche encounter |
| Birth with useful tools | One reviewed birth, retained Source/workset, installed authoring/Make capabilities | Hamm Creek House born; checked Host authoring and Crèche used; full toolset remains limited |
| Wake and next Seed | Same Body, authored/checked Host definition, admitted Make and exact artifact | Body-authored timer Seed verified; graphical successor not yet made |
| Deployment and admission | Explicit carrier or human transfer, actual new Boot and authorized same-Body member | Physical Threebee timer Seed Boot/admission verified; graphical deployment pending |
| Grow | Same recognizable path for RP2040, ESP32, Pi and browser | Not achieved |
| Continue and present | Sensing/recording/interaction under exact Plans/Lines; coherent actual Faces/Shows | Not achieved |
| Reproduce | Source, commands, chronological receipts, images and physical evidence | This record begins that evidence; whole journey remains open |

A smaller fixture, a manually assembled Rust owner, a caption rename or copied
BodyId cannot satisfy those stages. Extract a shared mechanism only when the
next actual stage demonstrates its need. Existing issues own the scope; no
parallel environmental framework is introduced.

## Checked equipment and programmable composition

Each Host definition must declare its actual physical attachments and selected
Base implementations: for example a DHT11 data GPIO, or a BME280 I2C bus/address.
Checked construction must resolve those selections into the appropriate standard
semantic Gear Kind implementations. A GPIO resource reservation alone is not
sensor support; a checked declaration alone is not an initialized ready offer.
Admission still uses actual initialized providers, finite resources and authority.

The retained Yellow definition already records DHT11 GP3 and TM1637 GP7/GP6 in

whole checked-definition-to-offer-to-Play path is installed. Do not replace this
path with a device-name switch in an environmental owner.

An authored Plot selects/composes the standard observation operations and routes
their typed feeds through admitted Cords/Lines into recording and graph
operations. Threebee realizes the resulting semantic graph through its Mask;
its display process must not secretly assemble or poll an independently defined
environmental application. Feed selection, composition and finite history/window
bounds must be programmable through ordinary checked source. Reuse existing
measurement and graph contracts where their meaning fits; illustrative names
such as `environment/current-temperature` are not new canonical Kind identities.

Keep the operation/value boundary open until the real provider contracts are
examined. The preferred direction is an observe/sample operation producing typed
observations: temperature is a semantic quantity, while observe, sample, publish
and retain describe operations. Do not preselect a temperature-specific Gear
Kind, or claim one general sampling contract can hide different device timing,
failures, available quantities or provenance. Compare existing observation and
quantity contracts before settling the exact Kind and Fore.

For each real device, retain the chain: checked Host configuration → selected
Base/provider implementation → actual ready offer → exact admitted Plan/Play →
typed observation provenance → authored graph contribution → acknowledged Show.
Changing equipment configuration must change construction/admission evidence;
changing a Look must not change this semantic chain.
